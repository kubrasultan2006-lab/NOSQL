Why monotonically increasing keys cause hotspots:
  Every new document has a key larger than all existing ones, so every insert falls into
  the chunk with the highest range (maxKey). That chunk lives on one shard, so one shard
  takes all the writes while the others sit idle. Splitting that chunk does not help,
  because the next insert again lands in the newest chunk. The balancer can only move
  OLD chunks to other shards afterwards, so the write throughput of the cluster stays
  limited to a single shard.
A hashed key spreads consecutive values across the whole hash space, so inserts are
  distributed evenly, but a range query on that field must ask every shard.

When a ranged key can still be appropriate:
  - Write volume is low enough for one shard (the hotspot does not matter).
  - Range queries on the key dominate the workload (time-window reports, scans).
  - The key is not monotonic: a compound key such as {tenant_id: 1, ts: 1} spreads writes
    across tenants and still supports a time range per tenant.
  - Zones or archiving rely on data ranges, for example the newest data on fast hardware.
